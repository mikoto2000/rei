# Failure Diagnosis → Repair

Enable `rei.repair.diagnosed-enabled` / `REI_REPAIR_DIAGNOSED_ENABLED` explicitly; default is false.
The CHAT workflow extends saved JUnit diagnosis, Text Change Set and SelfPatchRepair. It adds no model,
external agent, scheduler or parallel execution path.

1. Reproduce a failure and inspect its complete saved JUnit report with `diagnoseTestReport`.
2. Read the intended existing UTF-8 file with `readTextChangeSetBase` and independently choose a fix.
3. Call `proposeDiagnosedRepair` with `reportPath`, `change:{path,expectedText,replacement}`,
   `testCommand` and optional `timeoutSeconds`. This saves the diagnosis SHA, patch version, exact
   Change Set hash, selected command, timeout and Project/root/session together. It does not execute
   tests or change source files. Inspect with `inspectDiagnosedRepair` or `/repair show ID`.
4. Review the diagnosis, diff, command and `receiptSha256`. The human submits
   `/repair apply ID receiptSha256`. The actual captured user request must match exactly; strings
   generated by a model, source file or tool result cannot authorize apply. The ordinary full-capability
   command policy and approval flow also apply.
   A durable application guard on this Change Set rejects ordinary `applyTextChangeSet` and
   unguarded repair callers; only the verified diagnosed-repair service enters the protected apply.
5. Before execution, recheck report bytes, patch and Change Set baseline. Save a durable STARTED claim,
   then run the existing full verification cycle. A complete failure triggers a new report observation:
   the reported failing test identities must still match before the saved one-shot Change Set applies.
6. Run the complete test → static review → final test cycle on the new patch. Save every round and
   apply receipt, including the initial failure. No progress, stale content, timeout, truncated output,
   mismatched failures, incomplete inspection or unknown application stops the operation.

An invocation permits one saved repair, at most two verification rounds/four test commands, and at
most 32 changed patch files. Existing text bounds remain 64 KiB. Each command is 1–60 seconds, default
30, within one shared 180-second deadline including preflight; the existing repair service also retains
its three-repair ceiling for other callers. No additional model calls occur here: proposal generation
uses the ordinary parent CHAT budget. Commands are explicit, bounded, saved and approved; credentials
and control characters in command text are rejected. Reports older than seven days, future dated,
partial or without actual observed failing cases cannot support a proposal.

Ownership is captured, with exclusive human Run mode required for writes. READ_ONLY can inspect
the same session's proposal. Proposal and diagnosis link use the existing shared DataSource transaction.
History is limited to 128 repairs per Project and each saved record to 128 KiB. An exact CAS claim
precedes commands and writes. STARTED after interruption/crash and UNKNOWN require inspection;
startup never executes them. Failed or uncertain operations are not automatically replayed. Successful
repeated requests read the historical receipt and never repeat the writer. Existing file events/cache
updates are retained by the Tool's editing boundary.

Saved XML is an observation; it does not independently establish that a command generated that report
or prove a root cause. `VERIFIED_CHECKS` establishes same-patch command exits and mandatory static
checks, with their stated limits, rather than semantic correctness, test-selection completeness or
current Goal completion. Receipt success is historical; compare current hashes and reverify after edits.
Independent semantic review and Goal completion requirements build on this evidence separately.

Tests use SQLite persistence, exact human request guards, stale/foreign/READ_ONLY ownership, crash
claims, uncertain writes and shared deadline. A real Git/Shell fixture reproduces a failed command,
updates JUnit XML, applies the saved fix, runs both subsequent checks and confirms index preservation.
No live models or external service writes are needed.
