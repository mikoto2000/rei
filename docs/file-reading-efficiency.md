# File reading efficiency

## Phase 0 baseline

Base: `4ef43028`, Java 25, Windows 11. `ReadingMetricsTest.repeatableSearchBaseline`
creates one UTF-8 file with two distant hits and eight identical fixed-string queries,
context 0, one selected file, default byte/token budgets. No model is called.

| Application observation | Baseline |
| --- | ---: |
| Tool calls | 1 |
| Physical source reads | 1 |
| Decodes / line splits | 9 / 9 |
| Query-file scans | 8 |
| Generated JSON bytes | 1263 |
| Generated estimated tokens (conservative estimator) | 350 |
| Search elapsed, illustrative single run | 54.4 ms |

Elapsed time is diagnostic, never a CI threshold. Metrics refer to application operations,
not OS I/O. Generated bytes/tokens are measured at the file result envelope. Final prompt
estimated tokens are recorded at `ContextAssembler.confirmedDelivery`, after projection,
compression and paging. These include the whole prompt and must not be added to generated
tool tokens as though they were distinct model charges. Provider token usage is not inferred.

Counters are scoped by captured `AgentRunContext`, with at most 256 in-memory runs.
Duplicate source-body measurement uses path/version/line/content identities, bounded at
1024 identities per run; saturation is reported as unknown, not zero duplication.
`duplicateBodyBytes` describes generated records, whereas `wireDuplicateBodyBytes` describes
the projected response. Both count UTF-8 source text only, excluding JSON metadata and line
separators; they are bounded observations, not a byte-for-byte profiler of model input.
Disable with `-Drei.reading.metrics.enabled=false`. Reproducible fixture output is written to
`target/reading-benchmark/search.json`.

## Windows file replacement investigation

`ReviewContinuationTest.pendingRangesAndDeletedSourceRemainVisible` fails under the desktop
restricted process token with `AccessDeniedException` at `StorageBackup.writeAtomic`'s
atomic replace. It passes with the ordinary process token on the same Windows machine,
checkout and JDK. `Files.write` and `force` close their handles before replacement; the
temporary file is removed in `finally`, and migration ownership uses try-with-resources.
This evidence does not justify a production retry or sleep. Run Windows storage tests with
normal filesystem replacement permission; do not classify sandbox refusal as an application
regression. No production replacement behavior was changed.

The full regression also exposed legacy fixtures that initialize today's schema and then
lower `user_version`. They now remove `reading_state` before simulating the old schema;
production migration remains strict and is not changed to silently accept an existing table.
On this Windows/JDK 25 installation, `file.encoding` is UTF-8 but `stdout.encoding` and
`stderr.encoding` are MS932. Child-JVM fixtures that read captured logs with UTF-8 now
explicitly select UTF-8 stdout/stderr in their argument files. This fixes diagnostic log
decoding without changing production encoding or replacing process-exit assertions.

## Compatibility

Legacy read/search record constructors and their default JSON contracts remain supported.
New representations and cursor behavior are opt-in. Security validation must precede cache
reuse or persisted-cursor access. Acquisition history is not proof of current prompt presence.

## Phase 1

The same fixture now decodes and splits lines once per request instead of nine times.
`FileSnapshots` owns the immutable decoded rows; the existing 8 MiB source bound also bounds
retained decoded data, which is not shared across requests or authorities.
`SearchScanBatch` evaluates query predicates in a file-major scan while preserving each query's
case/regex/inversion/context/file-name-only settings, results, limits and errors.

`searchAndRead.request.compactOutput=true` selects a wire projection. Internal matches still
contain exact source. On the wire, a match whose full text is already present in a section
uses `sectionIndex` (zero based), `line` and `queryIndex`. A partial or absent section never
causes match text to be discarded. Default delivery is unchanged. Compare tokens with the
same estimator; no additional LLM call is made. `wireBytes` / `wireEstimatedTokens` measure
the converter output, separately from the internal generated JSON and final prompt.

## Phase 2

`searchFilePage` adds a persistent, run-scoped search API. `RESULT:<uuid>` resumes pending
hit neighborhoods; `SCAN:<uuid>` resumes exploration. Neither is a `readMultiFile.nextRead`.
Pass the returned cursor unchanged with optional new output/scan budgets. Retrying an old
cursor is idempotent: it describes the same source position, rather than consuming mutable
server position and risking lost results after a transport failure.

Search state lives in schema 19's `reading_state`, using `StorageDatabase` transactions.
Scope includes run, conversation, real Project root, project identity, request source and mode.
Retention is 24 hours, with 4 MiB per record, 2048 records and 64 MiB total. Expired records
are collected on writes. No stored body is returned before current path security checks.
An immutable inventory is saved once and referenced by subsequent cursors, rather than
copied into every page. Counters and restorable delivery metadata retain at most seven days.
Empty pages expose a stable query/inventory `scanId`; advancing completed file coverage is
finite acquisition progress. The evaluator persists a high-water position for at most 256
searches (20,000 files each). Cursor spelling, replay and earlier positions grant no progress,
including after checkpoint restart. This never marks review work complete or refills budgets.
The current inventory metadata is checked on resume; a pending file's SHA-256 must also
match its stored version. Changed files invalidate the cursor.

Each request bounds file scans and source bytes; oversized individual files return an explicit
failure while permitting the rest of the search to continue. Source files remain limited to
1 MiB; this change does not introduce streaming reads of larger files. The inventory safety
ceiling is 20,000 paths; exceeding it requires a narrower scope and is explicitly reported.
Query groups currently require one charset. Legacy ranked `searchAndRead` is unchanged.

Tests cover two distant hits, reconstructing the store, source edits, invalid cursors, and
1030 files with the last target reached through nine pages of at most 128 file scans.

## Phase 3

`ReadingDelivery` maintains current prompt presence separately from `InformationLedger`.
Only exact source rows in registered file-tool responses are eligible. Partial rows, unknown
arguments, Java signature displays and generic summaries cannot establish availability.
Old evidence is persisted as restorable metadata with a raw result reference; restart never
restores `AVAILABLE` without confirming a new prompt. A complete verified `readRawToolResult`
page can reestablish presence. Missing originals fail open to returning source.

`readMultiFile.files[].unreadOnly=true` suppresses a complete explicit line interval only if
all its versioned row hashes are present. Full-file reads always return source. Returned
`delivery` notices describe the last confirmed prompt, not read success. After history
projection, `ContextAssembler` checks suppressed results again and restores their exact
original rows before applying delivery budgets. Missing originals produce an explicit
restoration error rather than silently presenting an empty file.

Compression restoration is distinct from new information and shares the existing bounded
restoration budget (eight observations); the same version/range cannot mint repeated grace.
No token or replan budget is replenished. Generated, wire, final prompt estimates and reported
provider prompt tokens have separate metric names. Run counters and duplicate identities
persist in SQLite; diagnostic persistence failures do not fail a file read.

## Phase 4

Markdown requests accept `section`, `sectionPath`, `sectionId`, `headingLevel`,
`includeChildren` (default true), and existing `contextLines`. CommonMark 0.29.0 supplies
block source spans, covering ATX, Setext and fenced code. Initial closed YAML frontmatter
is masked with blank lines before parsing so source line coordinates remain unchanged.
The index contains top-level document headings, not headings nested in lists/quotes.
It bounds nesting and heading count, and retains skipped-level ancestry. Ambiguity returns
versioned candidates; choose the `line:<number>` section ID with `expectedVersion`.
Native file cursors retain the selection and version, including token-pager continuations.

`SourceEvidence` is the common path/version/line/selector/source identity representation for
reads and review pages. Its adapters do not repeat existing fields in the wire JSON. Review
plans, coverage, submissions and restart semantics remain owned by `ReviewCoverageLedger`;
acquiring source is never treated as completing a review. Search cursors own pending search
ranges, and the existing acquisition ledger owns historical read ranges. These different
notions of completion are deliberately not merged into a universal plan.

Restorable delivery history retains the newest entries fitting a 2 MiB serialized envelope,
and current availability is bounded to 64 runs / approximately 8 MiB of metadata. Dropping
history or failing to persist optional diagnostics never permits omission of unknown source
and never aborts an already confirmed prompt.

## Reproducible comparisons

`ReadingEfficiencyBenchmarkTest` writes JSON comparisons under `target/reading-benchmark`.
The repeated-line fixture compares the same internal results in legacy/compact wire formats.
The gap fixture uses identical 512-token output budgets, one context line and the same initial
one-line source budget; continuation uses the native reader versus the result cursor.
Markdown compares the same 200-section document and source budgets. Distinct-query scans
are measured separately. Timing is reported diagnostically, never as a pass threshold.

The seven requested scenarios map to: repeated-line and distinct-query benchmarks; the
distant-hit benchmark; the 1030-file cursor fixture; `ReadingDeliveryTest`'s compression and
raw restoration; `MarkdownSectionReadTest`'s hierarchy/long-section fixtures; and persisted
Run state plus `PagedFileSearchTest.cursorResumesInAFreshJvm`. The fresh-JVM probe verifies
actual process restart, not only reconstructing Java objects.

These deterministic tests make zero model calls. Returned-token estimates are not LLM total
input usage. End-to-end task completion/quality and provider input usage require a separately
configured live model evaluation; no live-provider improvement is claimed by these reports.

The distant-hit total is the sum of returned tool payload estimates, not repeated conversational
input to a model. Markdown selection answers a section request and is not interchangeable with
reviewing every section; the benchmark asserts the requested source is returned. Estimates
depend on the selected estimator. Generated JSON reports are local test artifacts and are
regenerated by the tests, rather than checked in with temporary paths and timing noise.

Phase 5 candidates are version-based diff retrieval, streamed large-file search, live model
task-quality evaluation, and measured concurrency/adaptive strategy. They are not enabled by
this change. Current file-size, inventory, charset and bounded-history limits remain explicit.

## Validation

On Windows / Java 25, the full non-live regression was executed and the affected tests were
rerun after fixes. The latest 1,189 suite reports contain 6,554 tests: 6,547 passed, zero
failures/errors, seven conditional skips. This is the aggregate of the full execution and
targeted reruns, not a claim that the first full invocation passed. The final related batch
covered 379 tests; the last recompiled 20-test batch passed after correcting child log encoding.
Twenty test methods were added across seven reading/search test classes, including the real
child-JVM restart probe. Existing review, native/API compatibility and stagnation tests pass.

The seven skips require opt-in native Windows/WSL Codex processes (three), optional unrelated
benchmarks (three), or a local PlantUML runtime (one). Live-provider tests are excluded by the
repository's `full` profile. The terminal reactor's 139 tests passed with no failures or skips.
Architecture/guard effectiveness tests pass. Checkstyle reports zero findings; SpotBugs has
1,868 grandfathered findings and zero new findings, with no static-analysis baseline expansion.
PR CI runs the final full suite independently before merge.

## Dependency boundary

| Component | Responsibility / reused implementation |
| --- | --- |
| `FileSnapshots`, `SearchScanBatch` | Request-local immutable bytes/decoded lines and file-major predicates; retain existing path/charset/search semantics |
| `SearchReadResultConverter` | Opt-in lossless compact wire projection |
| `PagedFileSearch`, `ReadingStateStore`, `ReadingStateMigration` | Separate pending-result / remaining-scan position; schema 19; existing serialized SQLite writer |
| `ReadingDelivery`, `ReadingRawAccess` | Confirmed prompt presence and exact restoration through the existing raw-result store |
| `ReadingMetrics`, `ReadingRuntime`, `ReadingRun` | Bounded diagnostics and host identity/estimator ports |
| `MarkdownSectionReads` | CommonMark selection translated into the existing native file reader and token pager |
| `SourceEvidence` | Shared immutable source coordinates for reads and review pages |
| `ReadingProblem`, `BoundedRegex` | Structured limits/errors and bounded Java regex evaluation |
| Existing `Tools`, `ContextAssembler`, `ProgressEvaluator`, `ReviewTools` | Tool contracts/security, prompt projection, bounded progress classification, review completion remain with their original owners |

Reading state, diagnostics, metrics and delivery live in the existing dependency-free
`tooldelivery` boundary. `ReadingRun` exposes captured identity without importing the run
engine. SQL and raw-result operations are ports bound to the existing `StorageDatabase`
serialized writer and verified raw store; path validation delegates to the original
Project/MCP boundary in `Tools`. No new business cycles, wiring cycles, UI dependencies
or dependencies into core are accepted by the architecture gate.

Four configuration pairs are individually registered in the D wiring budget for this
request's Phase 2/3: `ContextCompressionConfiguration` to `ReadingStateStore`, its `Work`
SQL callback, `ReadingDelivery`, and `ReadingRawAccess`. These are the new bean/port
bindings required to reuse storage and exact raw-result delivery. They are listed explicitly
for PR review; no generated report is copied into the budgets and no business-cycle budget
is widened. Future changes remain subject to the exact-pair gate.
