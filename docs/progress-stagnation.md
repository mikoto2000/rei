# 進捗判定と停滞からの復旧

## 既存機構との関係

進捗評価は `ProgressEvaluator`、反復集計と復旧は `RunExecutionContext`、局所カウンタは
`StagnationDetector` を拡張する。別のGoalやPlanning Loopは作成しない。
Read範囲は既存の `InformationLedger`、再開情報は既存SQLiteチェックポイント内の
`progress` JSONを使う。テーブルや既存データの書き換えは不要。

従来は範囲取得を `acquisitionProgress` として区別していたが、範囲が増える限り成果の停滞判定を
回避できた。また情報台帳だけを復元し、局所カウンタや再読の目的を復元できなかった。
今回、取得範囲の進展を保ったまま成果の進展を別途監視し、カウンタ・復旧履歴・復元枠も保存する。

## 進捗イベント

互換性のため `kind` の従来名を保持し、読み取り専用の `category` を追加する。

| category | 観測根拠 | 意味 |
| --- | --- | --- |
| INFORMATION_DISCOVERED | 未登録の返却内容の識別値、失敗の解消 | 情報の取得。成果完成の証明には使わない |
| COVERAGE_ADVANCED | 同じパス・版の未取得区間、実際に返された断片 | 調査対象範囲の拡大 |
| WORK_PRODUCT_UPDATED | 書き込み前後の実内容の変化、検証済みレビュー・Stage証拠 | 成果物・検証結果の進展 |
| STEP_ADVANCED | 初回の工程開始、DONEへの遷移、既存実行器のSubgoal成功 | 工程の進展。完了検証の権限は変更しない |
| CONTEXT_RESTORED | チェックポイント内の同一版・取得済み区間の有界な再取得 | 文脈復元。新規情報や成果として数えない |
| UNKNOWN | 追跡容量不足・旧履歴・不正な範囲情報 | 不明。進捗にも重複にも決めつけない |

Read成功で確定するのはFetchedだけである。Examinedを推測で確定しない。
Reviewedは既存 `ReviewCoverageLedger` の利用・配信・レビュー検証を使い、Readだけでは確定しない。
ActionPlanの開始を一度観測しても、そのReadが新規情報になったり、その工程が完了したりはしない。
再度同じ工程を開始しても開始イベントを追加しない。

`attachGoalStageEvidence` は保存証拠を添付した後、既存 `GoalStageVerifier` による独立検証結果を
返す。VERIFIEDかつ成果物版がある結果だけを成果の進展として一度認識する。
Stageの完了確定・後続工程の解禁は引き続き既存ホストの検証に委ねる。
モデルの説明、proofの添付、UNSATISFIEDだけでは成果の進展としない。

## Read範囲と保存上限

`InformationLedger` は正規化パスと返却された版をキーに半開区間をマージする。
部分重複は新しい行だけを数え、別ファイル・別版を区別する。要求行数でなく返却行数を使う。
バイト切り詰めで途中の行になった部分を全行として登録せず、返却端点と断片の識別値で重複排除する。
版は既存Read結果の値を使い、進捗判定のための全文再読や全文ハッシュは追加しない。
版情報のない従来ツールは既存の内容識別処理で扱う。復元猶予には確実に対応付けられる版付き区間が必要。

情報識別値は1,024件、ファイル・版とマージ区間もそれぞれ最大1,024件、取得元文字数は32,768。
成果・工程の重複排除も最大1,024件のSHA-256識別値として保存する。
古い識別値を追い出して既読情報を新規に戻すことはしない。上限時はUNKNOWNへフォールバックする。
情報識別値が満杯でも既存ファイルの連続範囲を拡張できる。
チェックポイント自体のサイズ・保持期間・改訂数の上限は既存設定が適用される。

## 局所停滞と目標停滞

Local Stagnationは観測できる変化がない反復で判定する。既定4反復。
新しい範囲の取得は局所停滞を防ぐ。ツール名・引数の同一性だけで停止しない。

Goal Stagnationは成果物・工程が進まない反復を別に数える。範囲取得だけでは解除しない。
連続する大量のページ取得を許容しつつ、成果整理へ移るため96反復の独立した判定窓を設ける。
既定のRun呼び出し予算120に対し、成果整理のための呼び出し余地を残す。
新しい範囲の取得はこの間も有効な調査進捗であり、局所停滞とは表示を分ける。
実際の成果物更新や工程進展で目標停滞を解消する。
既存の検索等の取得のみ32反復の判定も維持する。

## 中断・再開とCompression

実際のチェックポイント再開時だけ復元対象を固定する。対象は保存されたパス・版・区間。
同じ区間への復元猶予は一度で、全系譜で最大8回。同一範囲を繰り返したり再開を繰り返したりしても増えない。
復元対象と使用回数は既存progress JSONへ保存する。
成果・工程の進展または復元上限で復元対象を閉じる。準備中の情報取得は対象を閉じず、
復元に該当しない反復は通常どおり停滞カウンタへ反映する。失敗時は
`CONTEXT_RESTORATION_FAILED` として既存要約や保存情報の利用を促す。

正当な復元反復では既存カウンタを増やさず、リセットもしない。保留中の再計画も復元中だけ延期し、
新規情報の版数は増やさない。復元終了後に同じ操作を繰り返せば保存済みカウンタから判定を継続する。
履歴のない旧チェックポイントはUNKNOWNへ安全にフォールバックし、無条件の復元免除は与えない。

Context Compressionは既存のメッセージ投影・要約・配信管理を担当する。
圧縮や要約を行っただけでは新たな再開枠を作らない。Waiting/Dependencyの未解決状態観測は
従来どおり停滞反復から除外し、承認・ポリシー・所有者チェックも従来の境界を通る。

## 復旧と予算

既存の次回LLM呼び出しへReplan Noticeを追加する。判定専用のLLM呼び出しは増やさない。

| 原因 | 最初の復旧案内 |
| --- | --- |
| REPEATED_READ | 取得済み情報で判断を整理、未読範囲へ移動、再読理由を確認 |
| COVERAGE_WITHOUT_WORK / WORK_STALLED | 中間成果物を作成、完了条件と追加調査の必要性を確認 |
| 工程・その他の停滞 | 阻害要因と完了条件を確認し実行方法を変更 |
| CONTEXT_RESTORATION_FAILED | 対象・版を確認し既存要約を利用、復元不能情報を明示 |

2回目は実施済み復旧を明示して既存Planning Loopによる方法変更を促す。
同じ案内を無制限に繰り返さない。既定の局所復旧上限2回と、共有Runの
`rei.llm.output-limit.max-replans-per-goal`（既定2）の両方に従う。
情報取得や再開で共有再計画予算を回復しない。Output-limitの分割予算とは従来どおり別枠。
LLM・トークン予算も引き続き強制する。不明情報には既存の16反復ごと最大2回の診断を使い、
LLM回数制限が無効でも48反復で不明状態を停止できる。

成果・工程状態はツールバッチ終了後に集計してから既存チェックポイントへ保存する。
再計画予算を消費したときも次のモデル呼び出し前に同じ保存経路へ反映し、再開で払い戻さない。
通常のReadごとに新しいSQLite保存経路は追加しない。

## 診断と開発時の検証

既存 `ExecutionProgressPayload` のdiagnosisに、局所・目標判定、判定窓、工程ID、最後の根拠、
最近の操作のダイジェスト、試行済み復旧、消費済み共有予算、残工程IDを付ける。
停止時は同じ情報と復旧案内を既存の失敗結果へ伝え、従来のエラーコードを維持する。
文書本文やツール引数全文を診断に追加しない。

追加の主なテストは `MultidimensionalProgressTest`、`ProgressRestorationTest`、
`GoalStagnationTest`。SQLite再開は `PersistentCheckpointServiceTest`、
Stage独立検証は `GoalStageLoopTest` で確認する。既存の `LargeReadProgressTest`、
`PagedReadStagnationTest`、`EvidenceProgressTest`、`ProgressLoopSafetyTest` も維持する。

```powershell
.\mvnw.cmd -Pfull test
.\mvnw.cmd checkstyle:checkstyle
.\mvnw.cmd -DskipTests compile spotbugs:spotbugs
.\.github\ci\test-static-analysis-gate.ps1
.\.github\ci\static-analysis-gate.ps1
```

上限に達した対象や版・区間を特定できない旧Read出力に対して、ExaminedやReviewedを推測しない。
中間成果物または既存の完了条件・検証器を使い、観測可能な作業の進展を作る必要がある。


## 再開時の確認処理

工程表は実行開始時に対象プロジェクトの実体へ束縛する。非同期の反復終了通知や
診断のスレッドにプロジェクトスコープがなくても、別プロジェクトの工程表を参照しない。

`countFileLines` はパスと行数の新しい組み合わせ、`getShellProcessStatus` は
プロセスID・存在・状態・終了コード・出力の新しい観測を情報進捗として扱う。
行数は本文の取得範囲やレビュー済み範囲を増やさず、経過時間・日時・診断文の変化は
新しいプロセス観測にならない。これらの識別子は既存の有限台帳で保存・重複排除する。

実際の再開時の `checkpointShow` と `checkpointInspect` は、既存の文脈復元上限8回を
Readと共有する。同じタスク・確認ツールは各Runで一度だけ対象となる。
新しいRunでは残りの枠で再確認できるが、使用回数はRun系譜全体で保持し、
再開のたびに8回へ戻さない。同じRunでrevisionが増えても猶予を再取得できない。
以前の版で保存した確認済み識別子があっても、残り枠の使用は妨げない。
通常実行や同じRun内の繰り返し照合は
この対象にならない。消費済みの停滞・再計画予算は保持する。

詳細診断を持つ停止例外も従来の停止エラー型を維持し、公開APIとCLIには固定の安全な
停止理由を伝える。内部診断全文を公開せず、`Operation failed.` への退行を防ぐ。


## スキル参照と旧停滞状態の補正

`readSkillResource` の本文は、正規化したスキル相対パス・行位置・取得文字列を既存の
有限な情報台帳で追跡する。ページを進めれば情報進捗となり、同じ本文の再取得や版など
メタデータだけの変化では進捗にしない。スキル手順の取得を対象文書のレビュー済み範囲へ
昇格させない。

旧版がこのツールを未対応として保存した停滞は、実際の再開時に直近8操作だけを調べる。
成功したスキル読み取りと呼び出しID・Runが一致する元結果参照を使い、保存済みの実結果を
会話の所有権検証付きで取得する。各結果は最大65536文字、最大8件に制限する。
未記録の本文が確認できた場合だけ情報台帳へ補い、誤った局所停滞を解除して、最初の
モデル呼び出しより前に既存のチェックポイント経路で保存する。以後は台帳により重複排除する。
再計画予算・復元使用回数・目標停滞窓は保持し、全般的な再開猶予や予算の払い戻しは行わない。
証跡不明・取得不能・台帳容量不足のときは推測で補正しない。

再開文脈には消費済み回数と、既読資料の再取得より保存済み根拠を用いた中間成果・
未完了工程の検証へ進む案内を、既存の文字数上限内で渡す。


## 停止前のモデルへの診断通知

局所停滞が1回以上ある場合、次の通常モデル呼び出しへ現在の停滞回数・閾値、
消費済みの共有再計画回数、文脈復元回数、直近のファイル範囲の判定を渡す。
再開時に既に閾値へ達した状態も、最初のモデル呼び出しから通知する。
この通知は再計画ではなく、回数枠の消費・払い戻しや停滞カウンターの変更を行わない。

範囲の診断は直近の読み取りツールについて最大4件、パスは各256文字に制限し、
パスをJSON文字列の参照データとして扱う。取得済み範囲はレビュー完了の証拠ではない。
モデルには依頼の権限内で具体的な中間指摘を既存のレビューツールや成果物へ保存し、
根拠不足なら阻害要因を明示するよう案内する。工程表の言い換えだけでは進捗にしない。

通知は通常のコンテキスト組み立て・上限判定を通し、呼び出し単位で生成する。
会話履歴やチェックポイントへ通知を追加し続けず、実際の情報・成果物の進展で局所停滞が
解除されれば通知も除く。通知を無視した反復は従来の閾値と共有予算で停止する。


## 再開依頼と本文の引き継ぎ

ホストが照合した再開依頼では、モデルへ一律に「まず現在の状態を確認・再計画」と
指示しない。ホストの照合結果と保存計画を使い、依頼の権限内で既存根拠を中間成果へ
整理し、未完了作業を続ける。新たな差分や具体的な情報不足だけを追加で確認する。
結果不明の副作用の再実行には引き続き項目ごとの確認を要求する。読み取り専用の
継続依頼は、従来どおり保存済みの元依頼を使用する。

再開文脈へは直近64操作から、成功済みの readMultiFile を最大4操作だけ調べる。
操作・Run・呼び出しIDと一致する確認済み元結果参照を、会話の所有権検証付きで取得する。
各元結果は65536文字以下、抜粋は最大4件・各8行・各行120文字まで、パス256文字・版128文字。
プロジェクト外、失敗、形式不正、取得不能、出所不一致の本文は使わない。
抜粋全体は再開文脈の文字数上限の4分の1と実際の残り領域に収める。

抜粋には版・開始行・元結果参照を添え、部分抜粋と明示する。文脈全体も従来どおり
信頼できない履歴資料として扱い、現在の全文・レビュー済みと推測しない。
チェックポイントをモデルへ読ませ直すための追加呼び出しや猶予枠を設けず、
本文の復元だけで進捗カウンターを変えたり、再計画予算・復元回数を払い戻したりしない。


### 再開指示の履歴への再混入を防ぐ

明示的な再開では、以前にホストが生成した再開要求も会話ログ、保存ターン、互換メモリに残る。
新しい再開要求を修正しても、過去の「まず状態確認」を user メッセージとして再送すると、
モデルが古い制御要求を今回の依頼と混同し、消費済み予算のままメタデータ確認へ戻ることがある。

`ResumeContextAdvisor` は履歴を読み込む既存 advisor の後で、同じ再開対象タスクのホスト生成要求に
完全一致する過去メッセージだけを、今回のモデル入力から除外する。現行形式と以前の形式を扱う。
今回の最終 user メッセージ、元の依頼、ユーザーの追加条件、引用や加筆を含む文章、別タスクの履歴は保持する。
通常の新規 Run と読み取り専用モードには適用しない。過去のログ・保存ターン自体は変更しない。

これは入力の履歴境界の修正であり、停滞カウンター、再計画予算、復元 Read 数を戻すものではない。
実モデルの検証には合成文書・合成保存状態・合成履歴のみを用い、実タスクの完走と混同しない。


### 予算枯渇後の再開で既知の探索に戻らない

復元枠と再計画予算を使い切り、Local Stagnation が既に閾値以上の保存状態では、
次の反復が既知一覧の再取得だけなら停止する。これは正しい停止条件であり、
再開要求の文面変更やカウンターの初期化によって回避しない。

一方、判定器だけが既知一覧を持ち、モデルには一覧を渡していなければ、モデルが同じ探索を選びやすい。
再開文脈には、直近 64 操作中の最大 4 件の成功した listFile / findFile から、
出所を検証できた非空の一覧を 1 件だけ復元する。各一覧は最大 64 パス、各パス 256 文字までとし、
プロジェクト外・不正な結果は使わない。全一覧が文脈上限内に収まる場合だけ配信済みとする。
一覧は過去の観測であり、現在のファイル構成の完全性やレビュー完了を証明しない。

再開先 Run の EXCLUSIVE モード、消費済み再計画予算、復元 Read 上限到達、Local Stagnation、
配信済み一覧、CONTINUE のホスト照合、照合差分なし・結果不明の副作用なし、という条件が揃ったときだけ、
listFile / findFile / checkpointShow / checkpointInspect を当該モデル反復の選択肢から一時的に外す。
不足本文の取得・具体的な検索・権限内の成果整理には既存ツールを使える。
本物の新規情報や成果更新で局所停滞が解消すれば、次の反復で元の探索ツールを戻す。
通常 Run、読み取り専用・会話モード、残予算がある状態、検証できない文脈では通常の選択肢を維持する。
モデルが非公開のツール名を返しても、その反復の実行コールバックには登録されず実行されない。

この制御は追加の復元猶予を与えず、予算・閾値・永続状態・権限判定を変更しない。
既読本文の重複取得だけなら同じ停止条件が働く。復旧できない場合に成果や完了を捏造してはならない。
実保存状態を用いる検証は、実 DB の読み取り専用接続、実際の生結果、ローカルモデル、隔離先成果物で行える。
この検証は停止条件と実行境界の確認であり、実モデルによるレビュー完走の保証ではない。
