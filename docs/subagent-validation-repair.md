# SubAgent検証エラーの修復

SubAgent定義YAMLに `maxRepairs: 1` を追加すると、最終回答のJSON parse、共通envelope、resultSchema、任意の実行証跡照合の失敗を修復できる。既定0（無効）、上限3。数値以外・負数・上限超過は定義読み込み時に拒否する。既存定義は変更不要。

初回の実行と修復は同じRun、モデル、元のtask/context、Tool履歴、Permission、証跡を共有する。既存Tool実行を自動的に再生せず、回答に検証診断を付けて修正を求める。モデルが追加のread-only Tool呼び出しを選ぶ場合も、従来の許可・キャンセル境界を通る。未検証の回答を親へ返さない。

`maxSteps` は初回、Tool後の応答、すべての修復応答に共通する論理LLM呼び出し予算。修復ごとにリセットしない。たとえばmaxSteps=3で初回Tool呼び出しと不正な最終回答に2回を使った場合、残る修復呼び出しは1回。予算不足はMAX_STEPS_EXCEEDEDで停止する。maxRepairsまで使い切っても検証に通らなければFAILED。timeoutも全体で1回の期限を適用し、修復時に延長しない。

修復promptには元の会話と値を含まない検証診断を渡す。不正な最終回答は先頭16,384文字までに制限し、診断は指示として扱わないよう求める。検証はpromptと独立して毎回行う。自由文の意味判断や証跡からの推論の正しさを保証する機能ではない。

結果の `repairAttempts` は修復開始回数、`validationHistory` は失敗した回答ごとの診断配列。先頭が元のエラー。修復成功、timeout、cancel、修復中のモデル障害でも履歴を保持する。`validationErrors` は最終的な検証失敗の診断で、正常完了時は空。rawの失敗回答は履歴やログに残さない。履歴は結果を返すためのRun内状態であり、再起動後の自動再試行は行わない。

モデル接続、Tool実行、Permission拒否、出力打ち切り、timeout、cancelは修復対象外。妥当なFAILURE/PARTIAL結果も、そのまま返す。repairは同じ検証契約に沿う回答修正であり、タスク全体の自動再実行ではない。
