# チャットのストリーミング読み取りタイムアウト再試行

通常チャットでは、HTTP 応答の受信後や本文の途中で読み取りがタイムアウトした場合も、
失敗した一回のモデル呼び出しを同じ組み立て済み Prompt で再試行する。
既定は追加2回、`rei.llm.max-stream-timeout-retries` /
`REI_LLM_MAX_STREAM_TIMEOUT_RETRIES` で0〜3回を指定できる。0で無効。
無通信タイムアウト自体は既存の `rei.llm.read-timeout`（既定5分）を使用する。

再試行の境界は StagnationChatModel 内のモデル応答集約までで、ツール実行を含まない。
完了前の本文・推論・ツール引数は次の試行に引き継がず、正常に受信完了した応答だけを
ツール実行に渡す。前のツール呼び出しと保存済み結果を再実行しない。
これは新しい Run の起動やチェックポイントの自動 resume ではない。

再試行ごとに既存の共有 LLM 呼び出し予算を消費する。失敗した呼び出しも返金せず、
Run / Goal の累積予算・停滞予算・引数補正枠をリセットしない。
失敗した生成の使用量を0とせず、トークン上限が有効で使用量不明なら既存の
TOKEN_USAGE_UNKNOWN で停止する。キャンセル、全体期限、共有予算の停止を優先する。
待ち時間は100ms、200ms、400msで、キャンセルにより中断できる。

画面には再試行案内を表示し、失敗した本文を完了回答として残さない。
既存の message.completed で案内へ置換し、次の試行には新しい messageId / thinkingId を使う。
SSE の再送・Native の投影でも同じ境界を使用する。端末に既に出力した文字は消せないため、
再試行案内で中断を示す。最終回答・会話ログ・互換 ChatMemory には失敗本文を混ぜない。

対象は型で確認できるソケット / HTTP タイムアウトと既知の SDK・非同期ラッパーのみ。
任意の例外本文からタイムアウトを推測しない。ツール失敗、形式不正、出力上限、
権限拒否や任意の Run 全体タイムアウトはこの再試行の対象外。
独立した SubAgent の BoundedToolLoop と既存の opt-in retry は変更しない。
SDK 内部の HTTP retry は別枠であるため、この設定を実ネットワーク要求数の上限とはしない。

検証は同一 Prompt、部分本文・ツール引数の破棄、既存ツール結果の保持、上限・取消・
使用量不明、UI イベントと互換履歴を対象にする。ローカル HTTP サーバーから実際の SDK に
SSE 本文を一部返したあと無通信にする試験も行う。実プロバイダーへの課金付き試験は行わない。
