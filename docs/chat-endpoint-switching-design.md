# chat 用 LLM エンドポイントの動的切り替え設計案

作成日: 2026-11-24
状態: レビュー用。実装は未着手。

2026-11-25: 通常チャットの ChatGPT 利用枠対応を含む実装に向けて
[Phase 0 の棚卸しと SDK 検証](chat-endpoints-implementation.md)を開始した。
以下の旧提案より今回の要件と現行コードを優先する。接続先選択 UI はまだ未実装。

## 目的

Rei を再起動せずに、chat が利用する LLM の接続先を利用者が切り替えられるようにする。
接続先は名前付きマップで登録し、`/llm chat use` で上下キーと Enter による選択を提供する。

ここでいうエンドポイントは、Rei がアクセスする OpenAI 互換 LLM API を指す。クライアントから Rei サーバーへの接続先とは別の設定である。

## 合意済みの要件と提案の区別

合意済みの要件:

- 接続先を名前付きマップで定義する。
- `use` は上下キーと Enter で接続先を選択できるようにする。
- この段階では設計をまとめ、実装コードは変更しない。

以下はレビュー対象の提案であり、まだ確定していない。

- コマンド体系を `/llm chat list|show|use` とする。
- 名前を直接指定する `/llm chat use <name>` も提供する。
- 選択は Rei サーバー全体で共有し、次に開始するチャット実行から適用する。
- 初期実装では実行時の選択を永続化せず、再起動時は設定の `active` に戻す。

## 現状と変更が必要な理由

- `rei.llm.features.chat` は現在、単一の `LlmProperties.Server` として扱われる。
- `LlmProperties` は機能設定のコピーを返すが、実行中の選択状態を管理する仕組みはない。
- `LlmModelProvider.chatModel(feature)` は機能名をキーにモデルをキャッシュする。
- `LlmChatClientProvider.chatClient(feature)` は機能名をキーにクライアントをキャッシュする。並列モード用クライアントにも別のキャッシュがある。
- `ChatExecutionService` はチャット要求の構築時に、実行モードに応じたクライアントを取得する。

そのため、設定値の書き換えだけでは生成済みのモデルとクライアントに変更が反映されない。接続先、モデル、生成オプションを一貫した単位で選択する必要がある。

主な参照箇所:

- `src/main/java/dev/mikoto2000/rei/llm/LlmProperties.java`
- `src/main/java/dev/mikoto2000/rei/llm/LlmModelProvider.java`
- `src/main/java/dev/mikoto2000/rei/llm/LlmChatClientProvider.java`
- `src/main/java/dev/mikoto2000/rei/core/chat/ChatExecutionService.java`
- `src/main/java/dev/mikoto2000/rei/llm/capture/LlmCaptureCommand.java`
- `terminal/cli/src/main/java/dev/mikoto2000/rei/cli/TerminalClient.java`

## 設定形式

```yaml
rei:
  llm:
    features:
      chat:
        active: local
        endpoints:
          local:
            base-url: http://127.0.0.1:11434
            api-key: dummy
            model: local-model
          remote:
            base-url: https://llm.example.com
            api-key: ${REMOTE_API_KEY}
            model: remote-model
```

- `active` は起動時に選択する接続先名。
- `endpoints` のキーをコマンドと選択メニューの識別子にする。配列の添字は使わない。
- 各エントリーには既存の `Server` 相当の設定を持たせる。`temperature`、`max-output-tokens`、`fallback-to-default` などの既存オプションも維持する。
- マップ形式では、空の `endpoints`、存在しない `active`、空の `base-url` を起動時の設定エラーにする案とする。既定接続先も選択したい場合の表現はレビュー事項とする。
- URL は既存の OpenAI 互換接続先の正規化処理を使い、対応するスキームなどの検証を行う。
- 名前は空白を含まない安定した識別子とし、許容文字と長さの制限は実装時に定義する。

### 既存設定との互換性

既存の `chat.base-url`、`chat.api-key`、`chat.model` などの単一接続先形式も引き続き受け付ける。
旧形式は内部的に単一の接続先へ正規化し、既存の環境変数も維持する。
chat の設定がない場合も、従来どおり `spring.ai.openai` の既定接続先を使う。

旧形式と新形式を同時指定した場合は、優先順位による黙示的な選択を避け、設定エラーにする案とする。
ただし、同梱 `application.yaml` の旧形式と外部設定の新形式がマージされるケースを含め、Spring の設定バインドで互換性が成立することを確認する。
他機能の `rei.llm.features.<feature>` の設定形式は維持する。

## コマンドと操作

| コマンド | 動作 |
| --- | --- |
| `/llm chat list` | 登録名、モデル、現在選択中の印を表示する |
| `/llm chat show` | 現在の接続先名、表示用 URL、モデルを表示する |
| `/llm chat use` | 対話式の接続先選択を開く |
| `/llm chat use <name>` | 名前で接続先を切り替える |

対話式表示の例:

```text
chat の接続先を選択してください

❯ local   （現在使用中）
  remote

↑↓: 移動  Enter: 決定  Esc: キャンセル
```

- 初期カーソルは現在選択中の接続先に置く。
- 表示順は名前順など、環境によらず安定する順序にする。
- Enter で確定し、Esc または Ctrl+C で変更せずに戻る。Ctrl+C は選択メニューを閉じる操作とし、別の実行をキャンセルしない。
- 同じ名前を選んだ場合は変更なしと表示する。
- 未登録の名前を直接指定した場合はエラーにし、選択を維持する。
- 非対話環境では入力待ちに入らず、`use <name>` を使う案内を返す。
- 選択中にイベント出力が届いても表示と端末の入力状態を復元できるようにする。

切り替え成功時の例:

```text
chat の接続先を local → remote に変更しました。
次のチャット実行から適用されます。
```

選択の成功は接続確認の成功を意味しない。初期実装では切り替え時に LLM 呼び出しを行わず、通信失敗は次のチャット実行で既存のエラー処理に従って通知する。

## 適用範囲とタイミング

提案する初期仕様は、Rei サーバー単位の共通選択である。プロジェクト、会話、接続クライアントごとの選択は初期スコープに含めない。
複数クライアントが接続する場合、いずれかの切り替えが他の利用者の次回実行にも反映されることをヘルプで明示する。

チャット実行を受け付けて Run を作成する時点で、接続先設定のスナップショットを確定する。
モデルと生成オプションは同じスナップショットから取得し、その Run のストリーミング、ツール呼び出し後の続行、内部リトライに使う。
切り替え途中に旧 URL と新モデルなどが混在しないようにする。

実行中の Run は元の接続先を維持する。待機中、承認待ち、チェックポイントからの再開を同じ Run と扱うか、新しい選択を適用する実行と扱うかは、既存の再開ライフサイクルを確認して確定する。
プロセスをまたぐ再開にも接続先を維持する場合は、認証情報ではなく接続先名などの識別情報を保存し、登録がなくなったときは黙って別の接続先へ送信しない。

## 内部構成の案

1. chat 用設定を旧形式・新形式から共通の接続先カタログへ正規化する。
2. 選択状態を専用サービスで管理し、完全に検証した選択値を原子的に更新する。
3. Run 開始時に、接続先名と設定を含む不変の実行用スナップショットを取得する。
4. モデルとクライアントを、そのスナップショットと実行モードから取得する。
5. 対話式 UI と名前指定コマンドは同じ選択サービスを呼ぶ。

モデル・クライアントのキャッシュは、単なる `chat` や `parallel-<mode>` ではなく、接続先の識別子と実行モードを考慮する。
設定カタログを起動後に変えない初期仕様なら接続先名を利用できる。将来設定の再読込を行う場合は設定世代なども必要になる。
実行中の Run が保持する旧クライアントを、切り替え時に破棄しない。

`LlmProperties` 全体の可変値を逐次書き換える方法は採らず、設定カタログと現在の選択を分離する。
機能設定が現在 `Map<String, Server>` である点を踏まえ、chat 専用型の導入方法と Spring のバインド方法をレビューする。

### 既存機能への影響

- EXCLUSIVE・READ_ONLY・CONVERSATION の各モードで同じ接続先選択を反映する。
- 既存のフォールバック、タイムアウト、利用量計測、障害抑制、リクエスト記録を維持する。
- `fallback-to-default` は既存どおり明示的に有効な場合だけ適用する。名前付き接続先を順に試す意味には変更しない。
- サブエージェントは現在 chat モデルを参照しているため、親 Run と同じスナップショットを継承するかを決める必要がある。
- 音声補正は専用接続先がない場合に chat 設定を参照するため、追従範囲を明確にする。
- コンテキスト圧縮など chat のモデル・オプションを参照する周辺処理についても、同一実行内で整合することを確認する。

## コマンドの接続と端末 UI

既存の `/llm` は `LlmCaptureCommand` で登録され、`capture` サブコマンドを持つ。
同名のルートコマンドを重複登録せず、既存の `/llm capture` を維持したまま `chat` を追加する構造に整理する。

バックエンド内のシェルと HTTP API を使う `terminal/cli` の双方にコマンド経路があるため、表示と切り替えの責務を分離する。
上下キーの入力とメニュー表示は端末側で処理し、バックエンドへの要求では接続先名のみを送る。
バックエンドは登録名を検証して選択を変更し、任意 URL や API キーを切り替え要求から受け取らない。

HTTP 経路には候補一覧・現在値の取得と選択変更の操作が必要になる。既存のコマンド実行経路を使うか専用 API にするかは、現行実装に合わせて決める。
既存の認証・コマンド実行権限を適用する。クライアントでの未対応コマンドが LLM への通常メッセージとして送信されないことも確認する。
端末 UI は既存の `MeetingSelectionMenu` などの選択操作を確認し、利用できる部分を再利用する。
Web・デスクトップ画面への選択 UI 追加は別途スコープを決める。

## 秘密情報と履歴

- API キーはサーバー側で保持し、一覧、選択 API、コマンド出力、エラー、補完候補には含めない。
- URL に認証情報や秘密のクエリがある場合に備え、表示用 URL を安全に整形する。
- 切り替えによって以後の会話履歴やツール結果の送信先も変わる。履歴は維持し、過去の発言の自動再送による接続テストは行わない。
- 診断用に Run が使用した接続先名とモデルを記録する案とする。記録に認証情報は含めない。

## 初期スコープに含めないもの

- 設定ファイルの変更監視と接続先カタログのホットリロード。
- コマンドによる接続先の追加・削除・認証情報の編集。
- 負荷分散、条件による自動選択、名前付き接続先間の自動フェイルオーバー。
- 実行時の選択状態の永続化。必要であれば後続の設計で保存先と復元規則を定義する。

## 実装時の検証項目

- 旧設定・新設定・chat 未設定での起動と、混在・不正設定の検出。
- 外部設定と同梱設定のマージ、既存環境変数の互換性。
- 一覧・現在値・名前指定・同名再選択・不明名・対話キャンセル・非対話環境。
- 上下キーと Enter、Ctrl+C、非同期イベント受信後の端末復元。
- 切り替え後の新規 Run が新接続先へ送信され、実行中の Run は旧接続先を維持すること。
- 並行した切り替えと Run 作成で接続先・モデル・オプションが混在しないこと。
- 並列モード、ツールループ、リトライ、フォールバック、承認後の続行、再開の整合性。
- サブエージェント、音声補正、コンテキスト圧縮への影響。
- コマンド・API の応答やエラーに API キーが出ないこと。
- 既存の `/llm capture` と、未対応コマンドを LLM に送信しない挙動の維持。

## レビューで確認したい点

1. `chat.active` と `chat.endpoints` の構成と、旧形式との互換方針は適切か。
2. サーバー全体で選択を共有してよいか。会話・プロジェクト単位が必要か。
3. 選択状態の永続化を初期実装に含めるべきか。
4. Run 作成時の固定をどこで行い、承認・再開時にどの設定を使うべきか。
5. サブエージェントと chat 設定を参照する周辺機能をどこまで追従させるべきか。
6. 既定の `spring.ai.openai` 接続先も名前付き候補として選べる必要があるか。
7. バックエンド内シェル・ターミナル CLI・Web/デスクトップの対応範囲は十分か。
8. キャッシュの識別方法と既存のフォールバック・記録・障害抑制との整合性に不足はないか。

## Responses 対応との共通境界（2026-11-24）

Responses Phase 0 は `ResolvedLlmEndpoint` を共通の不変値として導入する。
API形式、互換性世代、認証の参照、能力、モデル、生成上限、timeoutをまとめる。
秘密値はこの値・fingerprintへ含めない。通常のAPIキーローテーションと、
認証主体・組織・プロジェクト変更による互換性世代更新を分離する。

現在の静的構成では、機能のモデルとOptionsに同じ構成スナップショットを使用する。
機能名キャッシュはこの固定構成の範囲内で有効である。将来の選択UIでは、
実効構成と実行モードを含むcache keyに変更し、古いRunの値を保持する。
設定Beanを逐次書き換えてキャッシュ済みモデルと新Optionsを混在させる方式は採らない。

Run受付での固定、承認継続、Checkpoint再開、親子Runの所有者検証は
Responsesの既存実行基盤への統合フェーズで同じ値を利用する。
未完了Runの接続先変更は原則拒否する。完了会話を別接続先へ引き継ぐ場合は
protocol固有情報を除いたテキスト履歴とし、推論payloadを別接続先に送らない。
この内部共通化によって本書の選択UIや`/llm chat use`が実装済みになるわけではない。
