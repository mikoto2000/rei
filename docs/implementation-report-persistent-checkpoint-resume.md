# 永続チェックポイント・Resume 実装報告

実装日: 2026-10-04。ブランチ: `feature/persistent-checkpoint-resume`。コミット hash は完了報告に記載します。

利用方法・設定・API は [利用ガイド](persistent-checkpoint-resume.md) を参照してください。

## 調査と判断

リポジトリと親ディレクトリの AGENTS.md を調べましたが、該当ファイルはありませんでした。DEVELOP.md、README.md、Run/Project の設計メモ、既存 Work Context・Checkpoint・Working Set・Run 管理・イベント・Shell プロセス・コンテキスト圧縮のコードとテストを確認しました。

作業開始時の作業ツリーはクリーンでした。途中で別の作業による README.md、DEVELOP.md、docs/program-structure.md の変更が入ったため、保持して今回のコミットから除外しました。

既存 CheckpointStore はプロジェクトスコープのメモリ上の最新1件で、永続タスク管理や明示 Resume の実行権はありませんでした。既存構造を残し、永続モデルとの連携を追加しました。既存 ActionPlan は状態モデルがあり、LLM 向けの更新入口はなかったため checkpointPlan を追加しました。

通常の新規チャットには新しいタスク ID を割り当てます。途中の追加指示は既存 intervention イベントからそのタスクへ記録します。明示 Resume だけが同じタスク ID と Session を引き継ぎ、新しい Run ID を作ります。Java スレッドや通信の復元は行いません。

## Phase 1

- PersistentCheckpoint に元依頼・追加指示・受入条件・計画・工程状態・根拠・操作状態・関連ファイル・Git・プロセス参照・ブロッカー・中断理由・次工程・識別情報・Schema・リビジョンを保存します。
- TOOL_CONFIRMED、TOOL_FAILED、ASSISTANT_CLAIM、RAW_RESULT_REFERENCE を区別します。計画の DONE はアシスタントの進捗記録であり、それだけで確認済み成果にはしません。
- 既存 SQLite DataSource に独立テーブルを追加しました。リビジョン・ヘッド・イベント重複防止キーを一つのトランザクションで保存し、期待リビジョンで競合を検出します。
- 正常な最新リビジョンをストリームで取得し、全履歴の読み込みを避けます。破損や Schema 不一致を診断し、古い正常データからの無確認 Resume は拒否します。
- Shell の保存・一覧・詳細・除外を実装しました。除外は履歴削除ではありません。

## Phase 2

- 保存境界を既存イベント体系と Tool dispatch に追加しました。Tool の実行予定、開始、確認済み成功、確認済み失敗、結果不明を区別します。モデルの Tool Call ID と Run ID を保存し、同じ Call ID が別 Run で使われても過去の不明操作を上書きしません。
- critical boundary の保存失敗を Tool 実行者へ伝えます。副作用前の保存失敗では Tool を呼ばず、副作用後の結果保存失敗では STARTED を残します。通常 UI listener の失敗隔離は維持しました。
- 計画・Tool・ファイル・プロセス・追加指示・Run 終端で保存し、トークン単位や保存のための LLM 呼び出しはありません。
- 照合は読み取り専用です。Git・関連ファイルの指紋・結果参照・管理プロセス・新しい Session Turn・未検証の完了主張を構造化して返します。プロジェクト全体の内容保存は行いません。
- 以前の所有プロセスが消滅した RUNNING 状態は、取得時に INTERRUPTED として提示します。PID と OS 起動時刻で所有権を判断し、生存する別プロセスの Run を奪いません。

## Phase 3

- 実行権取得、ロック後の再取得、照合、元依頼と進捗のコンテキスト構成、新 Run の保存、既存プロジェクトキューへの投入を接続しました。Tool 内で LLM ループを再帰的に呼びません。
- 不明操作がある場合は読み取りと確認・計画の Tool を許可し、変更操作を停止します。個別の結果確認は現在のユーザー入力の `runId:toolCallId` と成功・失敗の明示確認で行います。
- 保存内容はユーザー入力とは別の SystemMessage に参照データとして注入します。過去の Tool 結果や承認を新規指示として扱わない方針を明記し、各セクションを文字数で制限して既存 ContextAssembler の hard limit を通します。
- キャンセルは既存 Run の仕組みを使います。Shell の照合中も既存キャンセルに登録し、キュー待ちのキャンセルと Run 終端で実行権を解放します。終端保存のために Git やファイル指紋の取得をやり直しません。
- Shell・Chat Tool・認証済み Web API は同じ Application Service を利用します。Web Resume は既存 Run Registry、キャンセル API、SSE と連携します。
- 既存 WorkContextAutomation の同じ Session の Run 終端更新を利用します。チェックポイント保存は Work Context の抽出成功に依存しません。

## 保存設定と制限

標準保存先は `<rei-data-dir>/memory.db`。Schema version 1 の JSON と SQLite のリビジョン・実行権・重複防止テーブルを使います。

初期値: 有効、10,000 イベント/リビジョンキー、スナップショット本体合計 64 MiB、1件 256 KiB、過去リビジョンの保持期間90日、再開コンテキスト12,000文字です。最新の正常なチェックポイントは期限だけでは削除しません。削除済みイベントの重複防止キーは保持し、件数上限に含めます。上限超過では以前のデータを保持して明示エラーを返します。

計画は100工程、操作台帳は500件を上限とし、通常の結果根拠は直近200件を中心に保持します。関連ファイルは既存 Working Set と旧 Checkpoint の参照を引き継ぎます。大きな Tool 結果は既存 RawToolResultStore に保存し、原文参照と実際のモデル Tool Call ID だけを記録します。

## 検証

TDD では永続 Repository と照合の未実装による Red、キュー待ちキャンセル後に実行権が残る Red、Tool 開始保存中のキャンセルで副作用が実行される Red を確認して Green にしました。関連テストを小さく実行してから全体の回帰テストを実施しています。

| 境界・要件 | 検証 |
| --- | --- |
| 再起動、プロジェクト分離、履歴 | SQLite を開き直す Repository テスト、独立 JVM Smoke |
| 重複イベント、並行更新、保存の原子性 | 同一イベント再処理、CyclicBarrier の2 writer、INSERT 障害注入 |
| 副作用後・結果保存前の中断 | Tool の副作用カウンタと結果 INSERT の障害注入。STARTED が残ることを確認 |
| 結果保存後・工程更新前の中断 | SUCCEEDED と TOOL_CONFIRMED の維持 |
| 実行権取得後の中断 | 独立 JVM の終了、次 JVM での実行権回復 |
| PID 再利用 | 現在 PID に異なる起動時刻を保存し、古い所有権として回復 |
| 不明操作の再実行防止 | mutating Tool を拒否し、read Tool を許可 |
| キャンセル | キュー待ちの解放、再開 Run の実際の ChatExecutionService の LLM キャンセル |
| Tool 開始保存中のキャンセル | 保存直後のキャンセル再確認により副作用カウンタが0のままであることを確認 |
| ファイル保護 | 変更検出後も現在のファイル内容が変わらないことを確認 |
| 巨大な結果・予算 | 大きな結果本文はスナップショット外、1,024文字設定のコンテキスト上限 |
| 破損、保持期限 | 破損尾部からの正常リビジョン取得、保持期限後のイベント重複防止、正常リビジョン保護 |
| HTTP と認証 | 実際の HTTP アプリを2回起動。保存→キャンセル→終了→状態変更→照合→Resume。未認証401と新 Run の202受付 |

独立 JVM の Smoke は実プロセス終了を伴います。HTTP Smoke は Spring Web アプリを終了・再起動し、実際の HTTP を使います。いずれも外部公開・デプロイ・実 LLM は使わず、制御された実行者を使っています。稼働中の本番アプリや Native Client を手動で再起動する検証は実施していません。

全体テストの最初の実行は 2,643件中、旧仕様の「トップレベル resume がない」テスト1件のみ失敗しました。会話の `/session resume` と新しいタスクの `/resume` を区別する仕様へ更新しました。最終回帰テストは 2,649件、失敗0、エラー0、スキップ0です。実行ログは `target/checkpoint-final-regression2.log` です。

## 未対応範囲

- Native Client の専用 Resume 画面・ボタン、独立した画像生成・要約などの Background Operation の Resume。
- OS プロセスへの再接続、VM・スレッド・LLM 通信の復元、Schema 移行・破損修復 UI。
- Git の変更巻き戻し、自動コミット、全会話からの一括生成、自動 Resume。
- 汎用 MCP / Shell の外部副作用の意味判断や、新しい承認エンジン。公開・送信・デプロイは既存の Tool 権限方式と現在のユーザー確認に従います。

新しいリビジョンの安全な保存・照合ができない場合は、既存の正常データを優先して残します。過去の承認は新 Run の実行権や個別確認として保存・転送しません。
