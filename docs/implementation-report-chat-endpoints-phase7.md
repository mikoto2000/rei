# 通常チャット接続基盤 Phase 7：承認後の継続と復旧

Phase 6 の通常マージ `8df11f16461bfffa709aa101d51b933fe00b0c88` を基点とする。
共通の Run、承認、Checkpoint、保護メッセージ、予算を使用し、接続種別ごとの別の継続機構は作らない。

## 承認済み入力の再開

承認待ちの推論入力は `Saved.inferencePending` で区別する。復元時は既に承認対象となった system、履歴、再開指示を最初の送信まで保持する。復元を契機とする review guidance や ContextAssembler の再生成で別の入力へ変わり、再び承認待ちになる不具合を修正した。

この扱いは最初の推論だけに適用する。公開ツールの現在の投影、保護メッセージの検証、内容 digest、現在の送信ポリシー、トークン予算、固定済み通信上限は引き続き検証する。実際の作業コンテキストが変われば、元の承認を消費済みにして変更内容への承認を取り直す。

## 承認待ち中の追加指示

追加の人間の指示を既存の承認文書へ直接追記しない。元の保護入力へ UserMessage を追加した新しい入力を保護し、新しい digest と一回限りの推論送信承認を作る。旧文書は監査用に保持し、承認待ちなら DENIED、承認済みなら CONSUMED にする。

文書・所有者・Run 状態・承認状態を確認し、短い SQL transaction 内で元の文書と状態が完全一致する場合だけ置き換える。文書の並行編集、再開処理による claim、別 Project からの操作は拒否する。保護本文の準備は独自 transaction との競合を避けて外側で行い、準備失敗・差し替え競合では未使用の新承認とその参照を整理する。元の有効な承認と入力は維持する。

接続、モデル、認証方式、アカウント登録世代、replay 方式、累積予算を追加指示によって変更しない。承認受付・復元・実送信時の照合は Phase 6 の共通基盤を使う。ツール実行権限は別途判定する。

## 検証の範囲

- 両 API × ContextAssembler 有効・無効で、承認対象の入力をそのまま一度送信する。実際のコンテキスト変更では新承認が必要になる。
- ChatGPT Plan と無認証 Responses × 3 モードで、実 SDK と永続 ToolDiscovery、SQL 承認を使う。再開ごとに実行コンテキストを作り直し、公開ツール集合と累積予算を復元する。成功済みの操作は一度だけ実行し、結果を次の承認対象へ含める。
- 両 Responses で、成功済み操作の後の EOF、failed、cancelled、incomplete による自動再送・操作の重複実行がないことを確認する。
- 二つの別 JVM を起動して、writer 終了後に reader が SQL の承認待ちを引き継ぐ。Plan/encrypted、ローカル Responses/encrypted・plaintext・none、Chat Completions/none の 5 構成で、保護本文、元の接続、成功済み tool prefix、予算、一回限りの grant を確認する。この試験の推論モデルは stub である。
- 既存の Checkpoint の跨 Run 復元、接続固定、繰り返し再開、Responses replay、受信バイト上限と再試行制限の回帰を実行する。

SDK の試験は DNS 前 interceptor または所有する loopback fixture を使用する。実アカウント・実ローカルモデル・実 app-server による推論は実行していない。これらの結果を実モデルとの互換性確認とは扱わない。
