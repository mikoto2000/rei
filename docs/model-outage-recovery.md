# Model outage recovery

### 推論サーバー障害後の待機

`rei.llm.outage-cooldown`（環境変数 `REI_LLM_OUTAGE_COOLDOWN`、既定 `30s`、範囲 `0s`〜`5m`）は、
接続失敗、タイムアウト、HTTP 5xx、SSE内のエラー等の後に新たなテキストLLM要求を控える期間です。
同じ接続先・モデル設定を使う機能間で共有します。待機後は1要求だけを復旧確認として通します。
待機中の新規対話要求は `model_cooling_down` で拒否します。既存の再試行処理が許可した
モデル要求と、終端 Run から起動する Work Context 抽出は、共有クールダウンと復旧確認枠を
非同期に待ってから送信します。送信前の待機はキャンセル可能です。待機だけでモデル呼出しを
増やしたり、ツールや Run 全体を再実行したりしません。

Work Context は待機も含めて既存の1バッチ60秒・更新全体240秒を消費します。
クールダウンや先行する復旧確認がその期限内に終わらなければ保存せずタイムアウトし、
後で明示更新できます。一般の待機もクールダウン設定値+1分を上限とし、永久に枠を保持しません。
復旧確認のストリームがキャンセルされた場合は、その確認枠だけを解放します。
`request sent` は実際に待機を通過して送信を開始する時点で出力し、待機による拒否を送信件数に含めません。
認証失敗、ツール引数エラー、ユーザーによる取消はこの待機を開始しません。
ストリームの一部を既に受信している場合は、途中から別モデルへ切り替えず失敗として扱います。

SDK 内部のテキスト要求再試行は無効にし、Rei の既存の再試行回数・呼出回数・使用量予算だけで
追加の要求を管理します。`rei.llm.read-timeout` は通信の無応答時間の上限であり、生成が継続している
要求の総経過時間ではありません。タイムアウトはサーバープロセスの停止を意味せず、
重い生成や他要求の処理によって応答が止まった場合もクールダウンの対象です。

サーバーが `RingFailed` や Engram 読み出し失敗を返す場合、Reiのログだけでは原因を確定できません。
サーバー側で該当時刻の推論プロセスのログ、各rankの終了理由、ディスクI/O・空き容量・メモリを確認してください。
Reiはサーバーの再起動・設定変更を自動では行いません。

作業状況の画像認識と音声補正の専用経路は、この実行イベント付きテキストLLMの待機制御の対象外です。
